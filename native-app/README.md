# Wynko native app (Expo / React Native)

A truly native mobile app for Wynko, meant to replace the Capacitor
wrapper in `../mobile/` once it reaches parity. The desktop app stays on
Tauri and keeps mirroring the website.

Screens render with real platform components (native tab bar, native
navigation stacks, native text inputs and switches), not a WebView, so
it stops feeling like a website, and it does not depend on how the web
app is built, so moving the website to Next.js later does not affect it.

`../mobile/` is untouched and still builds as before.

## Run it

```
npm install
npx expo run:android   # builds the dev client with the Focus Lock module
npx expo run:ios       # needs a Mac with Xcode
npm run typecheck
```

`android/` and `ios/` are generated by `expo prebuild` and gitignored.
Everything native lives in `app.json` and `modules/`.

Expo Go works for the UI but not for Focus Lock, because the blocking
module is custom native code. Use a dev build (`expo run:android`, or
EAS Build) for that.

Google sign-in returns to the app on `wynko://auth-callback`. Add that
URL under Supabase > Authentication > URL Configuration > Redirect URLs.

## Layout

- `src/app/` routes (Expo Router): `login`, and the `(tabs)` group with
  Home, Focus Lock, Groups and Profile
- `src/lib/supabase.ts` the same Supabase project as the website,
  with sessions stored in AsyncStorage
- `src/lib/auth.tsx` session context, email and Google sign-in
- `modules/wynko-locking/` Android blocking as a local Expo module

## What carried over from the Capacitor app

The on-device blocking is already native Kotlin, so it moves across
almost unchanged. `modules/wynko-locking/android/` holds copies of
`BlockStore`, the Accessibility service (app blocking overlay), the
local VPN service (website blocking) and the Device Admin receiver, with
the package renamed to `com.wynko.locking`. Only the bridge was
rewritten: `RevM2LockingPlugin` (Capacitor) became `WynkoLockingModule`
(Expo Modules API) with the same method names and result shapes, so the
session logic in `blocks.html` (`syncSessionToMobile()`) maps across one
to one.

Also reused as is: the Supabase project, tables, RLS and RPCs; the
design tokens (`src/lib/theme.ts` mirrors `src/styles/tokens.css`).

## What has to be rebuilt

Every screen. The website is about 20k lines of page HTML with Supabase
calls written inline, so the order that makes sense is:

1. Pull the Supabase queries for each feature out of the HTML pages into
   plain TypeScript functions both apps can import (a `packages/core`
   workspace fits well with a future Next.js site).
2. Rebuild screens on top of them: Focus Lock / blocks, study tracker and
   timer, groups and chat, battles, Wynky, shop and wallet, onboarding.
3. Chat and partner calls use WebRTC in the browser; natively that needs
   `react-native-webrtc`.
4. Push notifications (`expo-notifications`) instead of web push.

## iOS blocking

There is no iOS app today, and Android's approach does not exist there.
iOS blocking has to use Apple's Screen Time APIs (FamilyControls,
ManagedSettings, DeviceActivity):

- Apple must approve the Family Controls distribution entitlement
  before any build can ship to TestFlight or the App Store. Request it
  early; it takes weeks.
- Apps cannot be listed by name. The user picks them in Apple's
  `FamilyActivityPicker`, and the app only gets opaque tokens, so the
  blocklist can't be synced from Supabase as package names the way
  Android does.
- Scheduled blocks run in a DeviceActivityMonitor app extension and the
  block screen is a ShieldConfiguration extension. Both are extra Swift
  targets, added through a config plugin (for example
  `@bacons/apple-targets`) or a library such as
  `react-native-device-activity`.
- Website blocking uses ManagedSettings web domain restrictions instead
  of a VPN.

## Play Store risk

Accessibility, VPN, `QUERY_ALL_PACKAGES` and Device Admin each need a
declaration in Play Console. This is the same risk the Capacitor build
already carries; moving to Expo neither adds nor removes it.
